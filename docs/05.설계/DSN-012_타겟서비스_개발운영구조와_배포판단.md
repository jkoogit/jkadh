## 1. 목적

본 문서는 BLG-028의 처리 기준에 따라 JKADH의 첫 타겟서비스 후보, 첫 가치 업무, 개발 운영구조, 저장소 관계와 현재 배포 필요성을 실제 저장소 evidence로 판단한다.

JKADH 플랫폼 변경과 타겟서비스 변경을 한 Issue나 PR에 섞지 않고, Harness가 Control Plane으로서 통제할 최소 경계를 정하는 데 목적이 있다.

PDFowers는 가상의 `sample-service`가 아니라 실제 기능 개발과 배포 검증이 진행되는 타겟서비스다. Issue #143에서 PDFowers ProjectProfile과 target-aware preflight를 최소 구현했으며 WorkOrder의 target/service Issue 저장 모델은 아직 후속 판단 대상으로 남아 있다.

Issue #141의 재검토에서도 PDFowers의 열린 Issue와 PR은 각각 0건이었고, `task/이메일인증구현_codex` 작업트리에는 이메일 인증 관련 코드, migration, 문서와 테스트 변경이 계속 남아 있었다. 따라서 타겟서비스 적용 필요성 Research는 재개할 수 있지만 동일 작업트리에서 첫 service pilot을 시작할 수는 없다.

현재 Harness 구현과 DSN-012 요구의 대조 결과는 다음과 같다.

| 항목 | 현재 구현 | PDFowers 적용 판단 |
|---|---|---|
| ProjectProfile 로딩 | 공통 필드와 기준 branch, PR base, 승급 branch, branch 정렬 정책을 지원하고 `pdfowers` profile을 등록했다. | JKADH 저장소 루트 기준 상대경로로 PDFowers를 참조한다. |
| 저장소 접근 확인 | `internal`은 허용, `env`는 차단 | 로컬 내부 저장소 read-only pilot에는 사용할 수 있다. |
| Git preflight | `project preflight`가 origin, AGENTS, lifecycle branch, 현재 branch와 tracked/untracked 상태를 확인한다. | `promotion` 정책에서는 환경 승급 branch SHA 비정렬을 허용한다. 현재 branch가 시작 허용 branch가 아니거나 tracked/untracked 작업 충돌이 있으면 blocker로 판정하며 profile에 명시한 runtime untracked만 제외한다. |
| GitHub preflight | 대상 repo의 열린 Issue/PR 수와 제목을 read-only로 조회한다. | 현황 확인은 가능하지만 target Issue와 WorkOrder 연결은 저장하지 않는다. |
| 작업 경계 저장 | HCP task에 scope, out-of-scope, completion, verification 저장 | 단일 JKADH task 경계는 저장하지만 `work_type`, target project/repo/path와 service Issue 연결이 없다. |
| 실행 lifecycle | 세션·태스크 lifecycle과 독립적인 `project preflight <project_id>` read-only 명령을 제공한다. | PDFowers 소스 변경, branch 생성, PR과 배포는 수행하지 않는다. |

`harness_task`와 `harness_task_event`는 migration, baseline과 테스트에 이미 반영되어 있으므로 후속 구현 후보가 아니다. PDFowers ProjectProfile과 target-aware read/check/report preflight까지 최소 integration 기반으로 구현했다. 실제 PDFowers 점검에서는 promotion lifecycle은 통과했지만 `task/이메일인증구현_codex`, tracked 변경 17건과 untracked migration 1건이 blocker로 확인됐고 허용 runtime 11건은 제외됐다. 다음 단계는 기존 이메일 인증 작업 정리 후 첫 service pilot 착수 여부를 확인하는 것이다.

## 3. 첫 가치 업무 판단

PDFowers 문서의 현재 우선순위 1은 다음 두 항목이다.

1. 이메일 인증 실제 API와 화면 흐름 구현
2. 계정 통합 승인 화면 UX 구현

이메일 인증은 가장 높은 사용자 가치 후보지만 이미 별도 작업 브랜치에서 미커밋 구현이 진행 중이다. JKADH 첫 서비스 사이클이 같은 작업을 새로 시작하면 변경 소유권과 완료 evidence가 충돌한다. 따라서 다음처럼 구분한다.

| 구분 | 판단 |
|---|---|
| 현재 제품 최우선 업무 | 이메일 인증 실제 API·화면 흐름 완성 |
| 현재 JKADH 신규 착수 | 제외. 기존 작업의 정리 전에는 수정하지 않는다. |
| JKADH 첫 service pilot 후보 | 이메일 인증 작업이 정리된 뒤 PDFowers 우선순위와 독립 Issue를 다시 확인해 선정 |
| 선행 integration pilot | PDFowers ProjectProfile과 target-aware read/check/report preflight를 최소 범위로 채택 |

계정 통합 승인 UX는 요구사항과 상태·버튼·메시지 기준이 구체화된 참고 후보다. 다만 현 세션에서는 타겟서비스 작업을 착수하지 않는다. Loop 기능 보완과 열린 Backlog 분류는 완료됐지만 PDFowers의 기존 이메일 인증 작업이 아직 dirty하므로, 해당 작업의 소유권과 완료 evidence를 정리하고 clean 작업환경을 확보한 뒤 첫 service pilot을 선정한다.

## 4. 개발 운영구조

작업 유형별 소유권과 산출물을 다음처럼 분리한다.

| 작업 유형 | 변경 저장소 | Issue·branch·PR | 책임 |
|---|---|---|---|
| `platform` | JKADH | JKADH에서 독립 lifecycle | HCP, 정책, 공통 ProjectProfile schema, evidence 관리 |
| `service` | PDFowers | PDFowers에서 독립 lifecycle | 제품 기능, 테스트, migration, 서비스 CI와 배포 구성 |
| `integration` | 기본적으로 JKADH | 저장소별 Issue·PR 분리 | ProjectProfile 등록, WorkOrder 대상 고정, 결과 링크 수집 |

하나의 사용자 주문이 둘 이상의 저장소 변경을 요구하면 저장소별 Issue와 PR을 분리한다. JKADH Issue는 orchestration과 evidence를 관리하고 PDFowers Issue는 제품 변경과 검증 결과를 소유한다. 두 Issue는 상호 링크하되 동일 브랜치나 동일 커밋으로 취급하지 않는다.

JKADH가 PDFowers에서 수행할 수 있는 초기 책임은 다음으로 제한한다.

- target repo, local path, base branch와 작업 유형 확인
- 타겟 저장소의 AGENTS.md와 작업트리 충돌 확인
- Issue, 범위, 제외범위, 완료조건, 검증방법을 WorkOrder로 고정
- 허용된 feature branch에서 작업하도록 확인
- 테스트, diff, PR과 배포 evidence 링크 수집
- Secret, 배포, main 영향, 외부 시스템 쓰기에서 사람 승인 요청

## 5. 저장소 관계와 책임

PDFowers는 JKADH 하위 디렉터리나 서브모듈로 편입하지 않고 별도 repo를 유지한다. 최소 ProjectProfile 후보는 다음과 같다.

```json
{
  "project_id": "pdfowers",
  "display_name": "PDFowers",
  "repo_full_name": "jkoogit/PDFowers",
  "local_path": "../PDFowers",
  "default_base_branch": "main",
  "task_pr_base_branch": "dev",
  "promotion_branches": ["dev", "stg", "main"],
  "branch_strategy": "feature",
  "allowed_work_types": ["service", "integration"],
  "harness_enabled": true
}
```

DSN-003의 공통 ProjectProfile에는 작업 PR base와 환경 승급 branch를 표현하는 필드가 없다. PDFowers는 작업 브랜치를 `main`에서 시작하지만 작업 PR은 `dev`로 보내고 `dev -> stg -> main`으로 승급하므로, `default_base_branch` 하나만으로는 실제 lifecycle을 표현할 수 없다. 이 차이는 ProjectProfile 구현 후속 범위로 분리한다.

## 6. 배포 필요성 판단

### 6.1 JKADH 플랫폼

현재 JKADH는 CLI, 문서, GitHub, HCP 상태와 DB 기반 Control Plane이다. 외부 사용자가 호출할 상시 API, UI, webhook consumer 또는 scheduler가 없으므로 플랫폼 자체 배포는 현재 필요하지 않다.

다음 조건 중 하나가 실제 요구가 될 때 배포를 재검토한다.

- 여러 사용자가 원격 API나 UI로 WorkOrder를 접수해야 한다.
- webhook, queue, scheduler처럼 상시 실행 프로세스가 필요하다.
- 로컬 HCP 상태를 중앙에서 공유·조회해야 한다.
- 원격 runner가 여러 타겟 저장소 작업을 배정·실행해야 한다.

그 전에는 로컬 CLI와 GitHub 기반 검증이 더 작은 운영 단위다.

### 6.2 PDFowers 서비스

PDFowers는 이미 Docker image build, NAS compose, 환경별 도메인·DB·OAuth·SMTP 설정과 smoke 기준을 보유하므로 배포 필요성이 존재한다. 다만 배포의 실행과 Secret 소유권은 PDFowers repo와 사람 운영자에게 둔다. JKADH는 배포를 직접 수행하지 않고 승인 여부와 결과 evidence만 연결한다.

### 6.3 GitHub Actions 우선순위

| 우선순위 | 적용 대상 | 판단 |
|---:|---|---|
| 1 | PDFowers PR의 typecheck/unit test/build | 배포보다 먼저 필요한 품질 gate다. 현재 dev image build만 있어 보강 가치가 크다. |
| 2 | PDFowers dev image build | 이미 적용되어 있으므로 유지한다. |
| 3 | JKADH Harness test/check와 상태 정합성 | 타겟서비스 작업을 차단하는 재현 문제가 생길 때 보조 태스크로 다룬다. |
| 4 | JKADH DB dry-run/validate/check | DB 변경이 있는 platform 태스크에서만 적용한다. |
| 5 | stg/prd 자동 배포 | Secret과 외부 시스템 쓰기가 있으므로 현재 자동화 채택 대상이 아니다. |

## 7. 한 턴 실행 사이클

첫 타겟서비스 service 작업은 다음 순서로 수행한다.

1. PDFowers의 기존 작업트리와 열린 Issue/PR을 확인한다.
2. 기존 미커밋 작업과 겹치면 중단하거나 별도 clean worktree 사용 승인을 받는다.
3. PDFowers Issue에 배경, 범위, 제외범위, 완료조건과 검증방법을 기록한다.
4. JKADH WorkOrder에 `work_type=service`, target repo/path, PDFowers Issue를 연결한다.
5. PDFowers AGENTS.md에 따라 `main` 기준 `task/한글-작업명_codex` 브랜치를 사용한다.
6. 제품 코드와 테스트는 PDFowers에서만 변경한다.
7. `typecheck`, 관련 unit/integration test, build와 diff를 검증한다.
8. PDFowers `dev` 대상 PR을 만들고 JKADH에는 PR과 verification evidence 링크만 기록한다.
9. 배포·Secret·외부 OAuth 수동 검증은 사람 승인 후 PDFowers lifecycle에서 수행한다.
10. 결과와 남은 gap을 각 저장소의 Issue/Backlog에 분리한다.

### 7.1 첫 service pilot 실행 계약

첫 service pilot은 기존 이메일 인증 변경이 정리된 뒤 **계정 통합 승인 화면 UX**를 우선 후보로 다시 확인한다. 착수 시점에 PDFowers 우선순위가 바뀌었거나 같은 범위의 기존 branch·Issue·PR이 있으면 후보를 자동 확정하지 않고 재선정한다.

| 항목 | 기준 |
|---|---|
| 범위 | 계정 통합 승인 화면의 상태, 버튼과 메시지 흐름 중 독립 테스트가 가능한 최소 단위를 PDFowers Issue 하나로 구현한다. |
| 제외범위 | 현재 dirty 이메일 인증 변경, 인증 DB migration 확장, JKADH Harness 코드, Secret·OAuth 설정, 배포와 branch 승급은 포함하지 않는다. |
| 완료조건 | PDFowers Issue와 JKADH WorkOrder가 상호 연결되고, `main` 기준 clean feature branch의 코드·테스트 변경이 PDFowers `dev` 대상 PR과 verification evidence로 남는다. |
| 검증방법 | PDFowers AGENTS 확인, 시작 SHA·dirty 상태 기록, 관련 typecheck와 unit/integration test, build, `git diff --check`, PR base/head와 변경 파일을 확인한다. |
| 중단조건 | 기존 작업과 scope가 겹치거나 작업트리가 dirty한 경우, Issue/WorkOrder 경계가 없는 경우, target-aware preflight가 branch lifecycle을 판정하지 못하는 경우, Secret·배포·외부 시스템 쓰기가 필요한 경우 중단하고 사람 승인을 요청한다. |

이 실행 계약은 다음 service 태스크의 입력 기준이며 현 Research 태스크에서 PDFowers Issue, branch, 코드 또는 배포를 생성한다는 뜻이 아니다.

## 8. Gap 분류

### 현재 태스크에서 필수

- BLG-030 해결과 열린 Backlog 분류를 근거로 BLG-132-001 Research 재개 조건을 확인한다.
- PDFowers의 열린 Issue/PR 0건과 dirty 이메일 인증 작업을 다시 확인한다.
- 현재 ProjectProfile, Git/GitHub preflight와 HCP task 경계 저장 구현을 DSN-012 요구와 대조한다.
- 최소 Harness를 PDFowers ProjectProfile과 target-aware read/check/report preflight로 제한한다.
- service pilot의 clean 작업환경, 독립 Issue/WorkOrder, 검증과 사람 승인 중단조건을 확정한다.

### 후속 Backlog

- WorkOrder target/service Issue 연결은 첫 pilot에서 현재 HCP task 경계만으로 부족한 evidence가 확인될 때 구현
- 실제 pilot에서 branch 판정이 차단될 때 `default_base_branch`, task PR base, promotion branch schema 보강
- 첫 service pilot의 검증이 부족할 때 PDFowers PR typecheck/unit test/build workflow 보강

### 채택 제외

- JKADH 플랫폼의 즉시 백엔드/API/UI 배포
- PDFowers 코드를 JKADH repo에 포함하는 구조
- JKADH가 PDFowers 배포 Secret 또는 배포 실행을 소유하는 구조
- 현재 미커밋 이메일 인증 작업에 JKADH가 병행 수정하는 방식
- `harness_task`, `harness_task_event` 중복 구현
- BLG-022, BLG-031, BLG-032, BLG-134-001 구현
- 타겟서비스 검토를 차단하지 않는 Harness 운영개선

### 추가 확인 필요

- PDFowers 이메일 인증 작업의 완료·PR 반영 시점
- 첫 service pilot 대상과 착수 시점
- NAS와 Cloudtype 중 최종 운영 위치
- ProjectProfile의 로컬 절대경로 저장 여부와 환경별 경로 주입 방식
- PDFowers service Issue와 JKADH WorkOrder의 양방향 링크 규칙
- 별도 clean worktree 사용 승인 여부

## 9. 후속 작업 후보

1. **PDFowers 이메일 인증 작업 정리 상태와 clean 작업환경 확인** (`read/check/report`)
2. **첫 PDFowers service pilot 선정과 실행** (1 완료 후 독립 PDFowers Issue로 수행)
3. **WorkOrder target/service Issue 연결 보강** (첫 pilot에서 현재 HCP task 경계가 실제로 부족할 때만 `platform` 후보)
4. **PDFowers PR typecheck/unit test/build CI 보강** (첫 pilot 검증을 실제 차단할 때만 `service` 후보)
5. **NAS/Cloudtype 운영 위치 확정과 stg/prd 배포 검증** (사람 승인 필요)

Harness 운영개선은 위 service 또는 integration 작업을 실제로 차단하는 경우에만 보조 태스크로 포함한다.
